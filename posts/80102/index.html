Gigabit Broadband Stuck at 300 Mbps: Two Local Bottlenecks

Created2026-11-26|Updated2026-11-26
|Word Count:1.6k|Reading Time:5mins|Comments:

家里办了千兆宽带，实测下载却只有 300 多兆。第一反应通常是打电话找运营商，或者怀疑光猫、网线。但这台机器上的数字有点奇怪：同一时刻、同一个 CDN，容器能跑到 700M，本机却始终停在 180M 左右——这说明问题不在宽带上，出口之后的路才值得怀疑。

这篇记录一次完整的排查：两个互相独立的瓶颈叠加在一起，一个在虚拟机网卡，一个在软路由 CPU。

一、先把现象测准

同一晚、同一批大文件（国内 CDN 的 electron 包，约 105MB），两个测点的对比：

指标 容器（走 veth） 本机 Win10（是虚拟机）
单流下载 约 350 Mbps 约 317 Mbps
多流峰值（钉死同一边缘 IP） 4 流 702 Mbps 4 流 181 Mbps / 8 流 181 Mbps
上传 约 31 Mbps 约 39 Mbps
国内 RTT 9.6 ms，0% 丢包 9 ms，0% 丢包

最值得注意的一行是多流：本机 8 条并发和 4 条并发跑出来一模一样，都是 181M，完全不随并发数增长；而容器在同一个边缘 IP 上能到 702M。带宽没跑满，但也不是单纯的慢——是某条路径撞上了一个不会随着并发变化而变化的硬顶。

二、天花板一：虚拟机里的 e1000 网卡

本机是一台跑在 PVE 上的 Windows 虚拟机，网卡用的是 e1000：

e1000 是 QEMU 全模拟的 Intel 网卡，不是 virtio 半虚拟化。它的毛病很明确：

  • 没有 RSS，收包全部压在一个队列、宿主的一个核上
  • RX 缓冲 256、TX 缓冲 512，队列浅，突发一来就丢
  • 接收路径大约在 180 Mbps 附近撞墙，加并发没用，因为瓶颈是单队列而不是连接数

这正好解释了 4 流 / 8 流都是 181M。对照组就在旁边：同一台宿主机上的 LXC 容器走 eth0@if5（veth 路径），同硬件同 CDN 能跑 702M——差的不是网络，是网卡虚拟化方式。

三、天花板二：软路由 CPU 打满

就算把本机的网卡问题解决，全屋出口还有第二道坎。软路由本身也是一台虚拟机，跑 PPPoE 和 NAT，配置只有 2 核 1GB。

下载期间采样 /proc/stat 算 busy 比例：

得到的结果是 96%～100% busy，而且不管下载是从本机发起还是从容器发起，都一样满。这说明它是全屋唯一的出口，卡在这里，整屋上限就被压在 540～700M。1GB 内存单核转发 + NAT + 连接跟踪，在千兆线速下本来就吃紧。

四、把其它可能逐个排除

排查最怕的是「换了一堆东西还是没好」。所以在动手前，先把容易误判的假设一条条测掉：

假设 实测方式 结论
CDN 给了不同节点 curl --resolve host:443:<edge-ip> 两条路径钉死同一 IP 排除
走了代理，出口不同 两边 WAN 出口 IP 相同 排除
局域网本身慢 本机 ↔ 容器 HTTP 拉 600MB，实测 760 Mbps 排除
路由器按 IP 限速 无 tc filter、无 nft 限速规则 排除
代理插件干扰 A/B 期间 nft 里相关规则 0 条 排除
宿主机上行不够 宿主直连测速 621 Mbps，网卡 1000Mb 排除

这两条尤其值得记住：

  • 钉边缘 IP：不然你以为的「限速」可能只是被分到了不同 CDN 节点。
  • 多流对比：单流慢是链路或对端问题；多流不涨，基本就是本地单队列/单核到了极限。

五、排查命令合集

六、改法（按收益排序）

  1. 把 e1000 换成 virtio：PVE Web UI 里删掉网卡重新添加，或者

改完必须关机再开机。Windows 里可能要重新装 virtio 驱动，MAC 变了记得同步 DHCP 绑定。这台机器还挂着显卡直通和 RDP，改网卡前先确认远程通道不会一起断掉。

  1. 软路由加核：从 2 核提到 4 核。想根治就换物理软路由，或者选支持多队列的 x86 方案——虚拟软路由的单核 NAT 在千兆下始终是薄弱环节。

  2. 观察期纪律：排查期间代理插件保持关闭，也别随手重启路由器，否则 A/B 实验作废，数据全部要重测。

七、验证与边界

已验证：qm config 确认了 e1000 与全模拟机器类型；容器侧确认走 veth；排除清单逐项实测；路由器 CPU 两次独立测量都复现 96～100%。

未验证：换 virtio 之后本机实际速率、软路由加核后的全屋出口速率。这两步都要停机，本次只做了定位，没有动手改。

几条边界写在这里，避免下次照抄结论：

  • 数据是在代理插件停用的观察期测的，恢复后绝对值会变，不能当基线
  • 结论是「瓶颈在本地」，不等于宽带本身健康——这次只验了出口 IP 和 RTT，没做运营商侧的业务测速
  • 「本机是虚拟机」这个前提会随拓扑变，每次排查先跑 qm config
  • 上传本来就受宽带上行限制（实测 30～40M），别把上传低当故障
  • 改网卡设置要进 PVE Web UI 或宿主机，虚拟机里的普通用户改不了

宽带不满速时，先花二十分钟把「谁是瓶颈」测清楚，比换光猫、换网线、换路由器省得多。
